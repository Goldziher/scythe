# Integration-test coverage exemptions.
#
# Read by tools/integration-test-generator/tests/coverage_completeness.rs,
# which runs under `cargo test --workspace`. Format, per section:
#
#   <key> : <reason>
#
# The reason is mandatory. Blank lines and lines starting with `#` are ignored.
#
# This list ratchets in BOTH directions and there is no tolerance mode:
#
#   * a key with no coverage and no entry here fails the build (regression);
#   * an entry here whose key IS covered now also fails the build (stale).
#
# So the list can only ever shrink, and every line is a specific, reviewed
# admission that something is not tested — not a percentage that a growing
# denominator can quietly improve.

[manifests]
# Backend manifests (name|engine) that ship but that no integration project
# exercises. Delete the line when you add the project.
#
# Common to every entry below: an integration project is only worth adding
# together with the CI job that runs it. A project committed with no CI step
# generates output that is checked for freshness but never executed, which is
# the exact shape of the defect this list exists to expose (see the
# csharp-snowflake note in .github/workflows/integration.yml, a binding bug
# that survived v0.6.0 -> 0.14.0 because its backend ran nowhere). Each entry
# therefore records the infrastructure the project needs, not just "TODO".

# R2DBC (reactive) across Java and Kotlin. The postgresql pair is closed:
# java.java.jinja and kotlin.kt.jinja now carry reactive harness branches that
# terminate every publisher in .block()/.collectList().block() (java) or await
# it inside runBlocking (kotlin), and both projects run 12 assertions in CI.
#
# The harness-branch mechanism therefore exists, and none of the four entries
# below is waiting on it any more. Each was generated, built and run against a
# live database, and each failed for its own driver-level reason:
#
# mysql -- LAST_INSERT_ID() is scoped to the connection that ran the INSERT,
# and the generated API takes a ConnectionFactory and wraps every query in
# `Mono.usingWhen(cf.create(), ..., conn::close)`, so each call gets a fresh
# connection and the follow-up SELECT sees no row. Measured: CreateUser ->
# "getLastInsertUser: no rows returned", then five cascading failures. The
# mysql fixture has no by-email lookup to substitute, so GetLastInsertUser and
# GetLastInsertOrder are simply not expressible against this API shape. This is
# a design question about the backend, not a missing harness branch. (The same
# LAST_INSERT_ID/pooling trap bit php-amphp on MySQL -- fixed there by narrowing
# the handle type, which has no analogue here.)
#
# mariadb -- the harness uses io.asyncer:r2dbc-mysql, which has no UUID codec,
# while the mariadb manifest maps `uuid` to java.util.UUID. Measured:
# "Cannot decode class java.util.UUID for VARCHAR" on the first query and
# "value must not be null" on every one after. The official, separately
# maintained org.mariadb:r2dbc-mariadb driver is the likely fix, but it needs
# its own MariadbConnectionConfiguration branch in both harness templates and
# a re-verification run -- not a dependency swap.
#
# sqlite -- there is no io.r2dbc:r2dbc-sqlite artifact published on Maven
# Central at all (verified 2026-08-14), and the one known community
# implementation, com.gitee.n__n:r2dbc-sqlite, is JitPack-distributed and
# untested here. Substituting r2dbc-h2 would not be a like-for-like swap: it is
# a different engine with a different dialect, so it would exercise neither the
# sqlite manifest's type mappings nor the sqlite schema fixture, and a green
# result would say nothing about the pair this line covers.
java-r2dbc|mysql : generated and run; LAST_INSERT_ID() cannot survive the per-query ConnectionFactory the generated API opens, so GetLastInsertUser returns no row
kotlin-r2dbc|mysql : generated and run; LAST_INSERT_ID() cannot survive the per-query ConnectionFactory the generated API opens, so GetLastInsertUser returns no row
java-r2dbc|mariadb : generated and run; io.asyncer:r2dbc-mysql has no UUID codec and the mariadb manifest maps uuid to java.util.UUID -- needs org.mariadb:r2dbc-mariadb and its own config branch
kotlin-r2dbc|mariadb : generated and run; io.asyncer:r2dbc-mysql has no UUID codec and the mariadb manifest maps uuid to java.util.UUID -- needs org.mariadb:r2dbc-mariadb and its own config branch
java-r2dbc|sqlite : no io.r2dbc:r2dbc-sqlite artifact exists on Maven Central; the harness branch is no longer the blocker
kotlin-r2dbc|sqlite : no io.r2dbc:r2dbc-sqlite artifact exists on Maven Central; the harness branch is no longer the blocker


# php-pdo on Oracle is blocked before the CI-infrastructure question even
# comes up. crates/scythe-codegen/src/backends/php_pdo.rs::PhpPdoBackend::new
# (php_pdo.rs:31-45) has no "oracle" match arm -- constructing the backend
# for engine "oracle" fails with InvalidConfig, and supported_engines()
# (php_pdo.rs:217-227) omits "oracle" too. crates/scythe-codegen/manifests/
# php-pdo.oracle.toml ships on disk but is deliberately unwired (see
# crates/scythe-codegen/tests/php_array_type_regression.rs). Wiring the
# manifest in is not enough on its own, either: for the Oracle dialect,
# crates/scythe-core/src/parser/mod.rs's preprocess_oracle_sql (mod.rs:567-595,
# invoked at mod.rs:329-331) strips a `RETURNING col1, col2 INTO :4, :5` clause
# down to a bare `RETURNING col1, col2` via strip_returning_into (mod.rs:747-758)
# before analysis, and that bare form is invalid Oracle syntax on its own
# (ORA-00925, missing INTO). Every Oracle backend that works today detects this
# stripped RETURNING and reconstructs a proper INTO/output-bind clause itself --
# see ruby_oci8.rs:207-253 and the identical pattern in python_oracledb.rs,
# csharp_oracle.rs, go_godror.rs. php_pdo.rs has no such logic. The pdo_oci
# (Oracle Instant Client) CI gap is real, but it is the second blocker, not
# the first.
php-pdo|oracle : blocked in crates/scythe-codegen/src/backends/php_pdo.rs (php_pdo.rs:31-45) -- no "oracle" engine arm and no RETURNING-INTO reconstruction like ruby_oci8.rs/python_oracledb.rs have; the pdo_oci CI extension gap is real but secondary

[ci-steps]
# Integration projects that no job in .github/workflows/integration.yml runs.
# Adding a project without a CI step produces output that is checked for
# freshness but never executed -- see the [manifests] preamble.
#
# These were issue #118. php-pdo-sqlite is closed: integration-sqlite needs no
# service container and already installs pdo_sqlite, so it only needed the
# `Test php-pdo-sqlite` step. ruby-oci8-oracle, kotlin-jdbc-ext and
# php-pdo-namespace are closed the same way -- each had a `test:*` Taskfile
# target already and no missing infrastructure, so each only needed its step
# added to integration-oracle or integration-pg.
#
# elixir-jamdb-oracle is closed too, but it earned its step the hard way: the
# step was added, failed immediately, and the failure was real -- the generated
# code had never been able to run at all. Fixed under board #223 and verified
# against a local gvenzl/oracle-xe:21-slim before the step went back.
#
# ruby-oci8-oracle is closed the same way jamdb was: its step ran, found a real
# defect (OCI8 returns a LOB locator where the row type declares String, board
# #225), and the fix went in with the step restored -- this time ordered last in
# the Oracle job, so a failure there costs only its own coverage instead of
# skipping the steps behind it.
#
# Only php-pdo-snowflake remains, for a reason different from "just add a step":
#
# php-pdo-snowflake needs the `pdo_snowflake` extension, which ships from
# snowflakedb/pdo_snowflake as neither a PECL package nor an apt package: it is
# built from source against Snowflake's C driver (cmake, a libcurl/openssl
# toolchain, and the vendored libsnowflakeclient submodule), copying the
# resulting pdo_snowflake.so and a cacert.pem into place by hand. That is a
# CI-infrastructure project in its own right, not a step modeled on a sibling
# -- this job has no sibling that builds a driver from source.
# go-database-sql-duckdb is closed: board #228's premise was understated. Measured
# against go-duckdb v2.3.3, a `*T` bind fails whether or not the pointer is nil,
# so the manifest's `nullable = "*{T}"` broke every nullable parameter, not just
# the NULL ones. The backend now dereferences at the bind site and the step runs
# in integration-duckdb alongside the other four duckdb projects.
php-pdo-snowflake : issue #118 -- pdo_snowflake has no PECL/apt package; it must be built from source against Snowflake's C driver (see snowflakedb/pdo_snowflake), which is real infrastructure work, not a missing step
